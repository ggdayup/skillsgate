### 3. NEW: `SkillRouter/.git/index.lock` — `git status` leaves a stale lock

Discovered because `git status` printed
`warning: unable to unlink '.git/index.lock': Operation not permitted`.

- **Reproducible, and repo-specific.** `git status` in `SkillRouter` creates a
  0-byte `.git/index.lock` and then fails to remove it. The sibling repo
  `skillsgate` (same machine, same shell, also Syncthing-synced) is clean.
- **Ruled out:** filesystem flags (`-`), ACLs (0 entries on both), xattrs
  (`com.apple.provenance` on both — identical), the sandbox (`python os.unlink()`
  inside `.git` succeeds), and a live git process (none).
- **Best remaining suspect:** two live `agy` (Antigravity CLI) processes with
  `cwd = SkillRouter`, each holding 20 fds under `.git` **including
  `index.lock`**, still resident at 06:23. Both are running **deleted `.old`
  binaries** (the on-disk `~/.local/bin/agy` was replaced 09-15 10:06), i.e. they
  predate that upgrade and are ~20 h old. Not proven, and **not touched** — they
  may be a live user session.
- **Workaround (verified):** `GIT_OPTIONAL_LOCKS=0 git status` → no warning, no
  lock. Mechanism confirmed: it is git's *opportunistic* index refresh that takes
  the lock.
- **Impact:** any `git add`/`git commit` in SkillRouter will fail on the stale
  lock until it is removed. Removed it twice with `rm`; it comes back on the next
  plain `git status`.

### 8. Git network tolerance — the user's three proposals, executed (07:35–07:47)

**Proposal 2 contained the important finding.** The service passes its guards as
`-c` on the git command line, and **`-c` overrides `~/.gitconfig`**. Proven with a
throwaway config rather than asserted:

```
GIT_CONFIG_GLOBAL=/tmp/probe git config --get http.lowSpeedTime           -> 60
GIT_CONFIG_GLOBAL=/tmp/probe git -c http.lowSpeedTime=30 config --get ... -> 30
```

So `git config --global http.lowSpeedTime 60` would have been **silently
ignored** by SkillRouter. The real fix had to go in the code.

**Code change (`08519d8`)** — both guards are now env-overridable:
`SKILLROUTER_GIT_LOW_SPEED_LIMIT` (default 1000) and
`SKILLROUTER_GIT_LOW_SPEED_TIME` (default **90**, was hardcoded 30). The 90 is
deliberate: it must stay BELOW the 120s fetch subprocess timeout, otherwise git
never aborts on its own and we are back to the original orphaned-grandchild bug.

**Runtime proof, from the log itself** — the warning prints the whole command
line, so the log shows which build is live: `'http.lowSpeedTime=90'` after the
07:42:56 restart vs `=30` before. Line numbers move predictably too:
`137` (pre-fix) → `187` (first fix) → `201` (this fix).

**Outcome**: fetches still fail sometimes (that is the network), but the re-clone
fallback now recovers them — at 07:44:29 the fetch failed and by 07:44:55 the
generation published normally, with **no `Git error syncing` ERROR following**.
The failure no longer propagates into a broken sync.

**Global config applied as asked** (`lowSpeedTime=60`, `lowSpeedLimit=1000`) —
useful for interactive git, inert for this service.

**Proposal 3 (SSH): already working.** `ssh -T git@github.com` returns
"Hi ggdayup! You've successfully authenticated". `~/.ssh/config` already routes
`github.com` via `ssh.github.com:443` ("port 22 unstable on this network") —
which is why SSH is healthy while HTTPS stalls. Caveat if switching the sources:
`~/.gitconfig` has `url.https://github.com/.insteadOf = ssh://git@github.com/`,
so **`ssh://`-style URLs get rewritten back to HTTPS**. Use scp-style
`git@github.com:owner/repo.git` to actually get SSH.

### 9. Root cause of the "git lock file" class: Syncthing was syncing `*.lock`

`~/.gitconfig` is a symlink into `~/ggdayup/SyncedConfig/`, a **separate
Syncthing folder**. Its `.stignore` excluded only `.DS_Store` and `._*` — not
lock files. So a `.gitconfig.lock` left behind by any interrupted write gets
**synced to every device sharing that folder**, after which
`git config --global <anything>` fails everywhere with "could not lock config
file ... File exists" for no visible reason. Exactly what happened here: the lock
held the fully-written new config, so only the final rename had been lost.

Fixed by adding `(?d)*.lock` + `(?d)**/*.lock` to `SyncedConfig/.stignore`.

**Ruled out for the SkillRouter `index.lock`**: the main `~/ggdayup-syncthing`
folder *does* exclude `(?d).git/` / `**/.git/**` and `(?d)**/*.lock` (via
`#include .stignore-shared`), so Syncthing is not the cause there. The two `agy`
processes remain the only correlate.
