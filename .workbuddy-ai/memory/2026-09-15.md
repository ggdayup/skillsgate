## Fixed the 3 core skills Antigravity couldn't parse

Antigravity logged `skills.go:199] Failed to parse skill file …` on every startup for
`verify-this`, `md-slides`, `mcpm-manager`. Root causes were two different bugs:

1. **`verify-this` + `mcpm-manager`** — unquoted `description` containing `": "`
   ("return exactly one verdict: VERIFIED" at col 162; "NOT for: writing" at col 255).
   Fixed by emitting the value as a YAML single-quoted scalar (`'` doubled). Round-trip
   asserted against pyyaml before writing.

2. **`md-slides`** — NOT a truncation issue. Its description contained the literal
   `` `---` ``. Any frontmatter extractor that does `content.split("---")[1]` cuts the
   block open at that inline `---`, leaving an unterminated `"` → go-yaml
   "found unexpected end of stream". Fixed by rewording to
   "horizontal-rule (HR) boundaries". This is why only 1 of 152 skills hit it.

**Reusable diagnostic**: scan every `*/SKILL.md` twice — once with
`re.match(r"^---\n(.*?)\n---\n", txt, re.S)` + `yaml.safe_load`, and once with
`yaml.safe_load(txt.split("---")[1])`. The second model catches the inline-`---` class
that the first one misses entirely.

After the fix: strict frontmatter failures 152 → **0**.

Also found and then fixed on request: `plan-first` had no `name`/`description` in its
frontmatter at all (only `triggers` + `not_for`), so agents could not match it. Added
both; `name: plan-first` matches the directory, and the 498-char description covers the
three-stage workflow plus the Chinese trigger phrases. When authoring a description by
hand, avoid `": "` entirely (some harnesses do `line.split(": ", 1)`) and quote it anyway.

Final state of the core set (152 skills): strict frontmatter failures **0**, naive
`split("---")` failures **0**, missing `name`/`description` **0**.

Backups of the originals: `/tmp/skill-backup/{verify-this,md-slides,mcpm-manager}.SKILL.md`.

### The DMG corruption reproduced, and is now fully diagnosed
`npm run package:mac -- --config.mac.notarize=false` exited 0 and produced a dmg that
`hdiutil verify` called VALID — but mounting it showed `Contents/Info.plist` **gone**,
replaced by a 3740-byte `.BC.T_zC7n4J`, plus a `.BC.T_8wVczg` where `PkgInfo` was. The
sandbox log listed 165 denied `file-write-unlink` operations, all under
`/Volumes/SkillsGate 0.6.2-arm64/...`: the sandbox renames each file it touches to a
`.BC.T_*` backup and then cannot unlink it, so the backups strand inside the mounted image.

**`hdiutil verify` only checksums the filesystem, not the bundle** — it is not a usable gate.

Fix that works: `release/mac-arm64/SkillsGate.app` is untouched (corruption is confined to
the mounted volume), so `hdiutil create -srcfolder release/mac-arm64 … -format UDZO` from
it yields a clean image (needs sandbox bypass). Then patch the dmg `sha512`/`size` in
`latest-mac.yml` and regenerate the blockmap with
`node_modules/app-builder-bin/mac/app-builder_arm64 blockmap` (note: `app-builder_arm64`,
not `app-builder`).

Final: dmg 121,333,036 B, sha512 matches `latest-mac.yml`, 0 `.BC.T_*` anywhere,
`codesign --verify --deep --strict` passes (ad-hoc), `app.asar` carries the split.
The `.zip` target is built from the app dir and was clean all along.

All of the above is now written up in `AGENTS.md` under "Packaging a macOS release
(DMG + zip)". Committed as `f7c26b9`.

## `npx skills add` 整合调研 — 发现两个工具在抢同一批磁盘路径

讨论「把 `npx skills add humanlayer/skills --skill show-me` 这种安装方式整合进
SkillsGate」时做的调研。**结论尚未定案，未改任何代码。**

### 上游 `skills`（vercel-labs/skills，npm 名就叫 `skills`，latest 1.5.26）的关键事实

1. **全局 canonical 目录 = `~/.agents/skills/<name>`**（`src/constants.ts`:
   `UNIVERSAL_SKILLS_DIR = '.agents/skills'`）——**与 SkillsGate 的 core skill set
   是同一个路径**。上游写入前会 `cleanAndCreateDirectory()` 先删后建，且没有
   `.store` 这个概念。这意味着上游 `-g` 安装会直接落进 core set（并被 fan-out
   到全部 agent），同时也可能删掉 core 里指向 skills-library 的相对 symlink。
2. **全局锁也是同一路径** `~/.agents/.skill-lock.json`。上游 `CURRENT_VERSION = 3`，
   SkillsGate `LOCK_FILE_VERSION = 1`，**两边都是「版本不匹配即清空」** →
   会轮流抹掉对方的安装溯源。
3. `-s/--skill` 是**贪婪变长、空格分隔**、`*` = 全部、**不切逗号**；SkillsGate 是
   单值、后者覆盖前者（`--skill a --skill b` 静默只装 b）。
4. 上游还有 `find`/`use` 命令、项目级 `skills-lock.json`（v1），SkillsGate 都没有。

### `npx` 解析机制（实测 npm 10.9.7 / node 22）

- **`npx` 完全不看 `$PATH`**（shell fallback 已被移除）。查询顺序：项目自身
  `package.json` 的 `bin` → 本地 `node_modules/.bin`（向上走到 `/`）→ npm global
  bin → registry。所以往 PATH 里放 `skills` shim 对 `npx skills` **无效**。
- **本地 bin 名冲突：静默 first-wins，赢家是「包名字典序最小」者**（实测，
  非文档化行为）。`skills` 是 `skillsgate` 的前缀 → **上游赢，shim 静默失效**。
- **全局 bin 名冲突：直接 `EEXIST` 硬失败**。所以若 skillsgate 声明
  `bin.skills`，已有全局 `skills` 的用户将**装不上 skillsgate**。
- **`npx skills@latest` 并不比 `npx skills` 更安全**（此前记录有误）：两者都经
  `latest` dist-tag 解析到同一版本，只是 npx 缓存目录不同。

### SkillsGate 现状（与整合相关）

- `skillsgate add X -s Y` **已可用**：`parseSource` → `cloneRepo` → `discoverSkills`
  → `filterSkills` → `installSkillForAgent`（`packages/cli/src/commands/add.ts`）。
- 桌面端 `skills:install-via-cli`（`apps/desktop/src/main/ipc-handlers.ts:1959`）
  是**死代码**：renderer 无任何调用点；硬编码 `--all --global -y`；source 被
  `replace(/[^a-zA-Z0-9_./-]/g,"")` 洗掉 `@`，导致 `owner/repo@skill` 变成
  `owner/reposkill`。
- `apps/desktop/src/renderer/routes/discover.tsx:667` 显示的
  `$ npx skills add {skill.source}` 对多技能仓库是**错的**（缺 `--skill`）。
- **桌面端目前没有任何「自由来源」输入入口**：`installSkill(source, …)`
  （`discover.tsx:874`）和 `coreInstall(source)`（`discover.tsx:889`）只在 catalog
  结果的 `skill.source` 上被调用（来源是 skills.sh 搜索），没有让用户手输
  `owner/repo` 或 URL 的地方。

### 需求澄清（用户 08:58 明确）

**`npx skills add X --skill Y` 不会被真的执行。** 它只是一个「通知 / 粘贴格式」：
用户在 SkillsGate 的 Mac GUI 的某个输入框里**粘贴**这个字符串，SkillsGate 把它
**解析成来源描述**（从哪装、装哪个 skill），然后走完全自研的安装链路。

因此：
- **不需要**劫持 `npx skills` 这个 bin 名、不需要 PATH shim、不需要碰 npx 解析
  —— 上面 §「`npx` 解析机制」那一节的全部风险**作废**（保留备查）。
- 桌面端 `skills:install-via-cli` 这条桥（会真的 spawn `npx skills`）**必须删掉**
  —— 它做的正是用户明确排除的事。
- 本质上是一个 **`parseInstallCommand()` 解析层**：把命令串归一化成现有的
  `ParsedSource` + skillFilter，下游 `cloneRepo` → `discoverSkills` →
  `filterSkills` → `installSkillForAgent` 一行都不用改。
- 上游 `~/.agents/skills` / lock 文件冲突（§1、§2）**与本需求解耦**，降级为独立
  隐患：只在用户自己另外在终端跑真 `npx skills` 时才触发。

## 跨项目诊断：SkillRouter 的 6.6 GB python3.11（2026-09-15 晚）

用户用 `lsof -p <pid> -a -d cwd,txt` 追到 `~/ggdayup-syncthing/code/SkillRouter`，
问怎么优化。**结论是「方向错了」——那 6.6 GB 不是 Python 内存，是 Metal/MPS 分配器缓存。**

### 诊断结论（用 vmmap，不是 ps）

- PID 1090：footprint 6.6 G（peak 6.8 G），cwd = SkillRouter，
  监听 `localhost:8768` = **SkillRouter WebUI（uvicorn）**，无客户端连接。
  - `IOAccelerator (graphics)` resident **6.1 G**（占 92%）
  - `__TEXT` resident 187 M（torch/python 代码页）
  - Python 堆（DefaultMallocZone）**仅 63.5 M**
  - `ReadOnly portion of Libraries: Total=1.3G resident=215.9M(16%)`
    → **torch 自己的 dylib 根本不是内存开销**
- PID 1078：footprint 2.9 G，其中 `IOAccelerator` 2.3 G，cwd = `/`，
  监听 `localhost:8765` = **SkillRouter MCP server，是活的**。

### ⚠️ 我在这里判错过一次（教训，必记）

最初我把这两个进程判成「孤儿、没人用、可以直接 kill」——**完全错了**。两个都在服役：
1078 有 **33 条 ESTABLISHED 连接**（opencode、agy 等客户端），
`/private/tmp/skillrouter_mcp.log` 的 mtime 就在 3 分钟前。

两个错因：

1. **`Parent Process: launchd [1]` ≠ 孤儿。** daemon 化（`nohup … &`、双 fork、包装
   脚本启动）同样会 reparent 到 launchd，而服务完全正常。它只说明「原父进程退出了」。
2. **配置查错了路径。** 我查的是 `~/.workbuddy-ai/mcp.json`，而活的是
   `~/.workbuddy/mcp.json`（L58 注册 `skill-router` → `http://127.0.0.1:8765/mcp`，
   `disabled: false`）。差一个 `-ai`，结论整个反过来。

**正确判据**：`lsof -p <pid> -a -i` 看有没有 ESTABLISHED（只有 LISTEN = 空闲），
`ls -la <日志>` 看 mtime，再 grep **正确的**配置路径。三者都静下来才谈得上 kill。

### 可复用的判据（重要）

**Mac 上 PyTorch 进程「内存暴涨」，先看 vmmap 里 `IOAccelerator (graphics)`。**
若它占大头，那就是 MPS caching allocator，不是泄漏、不是模型太大、不是 Python 堆。

配套 API（`torch/mps/__init__.py`，已在本机 venv 核实）：

- `torch.mps.driver_allocated_memory()` — **等于 vmmap 里的 IOAccelerator**（含缓存池）
- `torch.mps.current_allocated_memory()` — 真实张量占用（不含缓存池）
- **两者之差 = 缓存池 = 看起来像泄漏的那部分**
- `torch.mps.empty_cache()` — 把空闲缓存还给 OS（默认分配器永不主动还）
- `torch.mps.set_per_process_memory_fraction(f)` — 硬上限，f×recommendedMaxWorkingSetSize，
  超了直接 OOM；范围 0~2，0 = 无限制

env（`strings libtorch_cpu.dylib` 核实存在）：
`PYTORCH_MPS_HIGH_WATERMARK_RATIO`、`PYTORCH_MPS_LOW_WATERMARK_RATIO`、
`PYTORCH_MPS_PREFER_METAL`、`PYTORCH_MPS_FAST_MATH`、`PYTORCH_MPS_DISABLE_PREFILL_ATTENTION`

### 顺带发现的既有故障：SkillRouter git sync 连续失败 221 次

重启 gateway 后看日志，发现与内存无关的既有问题：

```
ERROR Failed to sync git source git_source_service.py:401
      src_e4660904cbea: Command '['git','-c','protocol.version=0','fetch',
      '--depth','1','origin','main']' timed out after 120 seconds
```

日志里 **221 次**，约每 20~25 分钟一次（20:52、21:12、21:37…），**与我的改动无关**。

**根因：陈旧的 git 锁文件。** `data_runtime/public/sources/` 下有 5 个：

```
src_e3ba1e9faf6e/repo/.git/shallow.lock
src_66348c51ffe0/repo/.git/shallow.lock
src_66348c51ffe0/repo/.git/objects/maintenance.lock
src_test/repo/.git/shallow.lock
src_test/repo/.git/objects/maintenance.lock
```

实测 `git fetch` 报 `fatal: Unable to create '...shallow.lock': File exists`，
而 `lsof` 查 **git 进程数 = 0** → 确认是死锁文件。

**根因（比初判更精确，实测确认）**：`subprocess.run(timeout=120)` 超时后
**只杀直接子进程**。实测抓到的进程链是 `git(43608) → git(43610) → git-remote-http(43612)`，
父进程是 gateway 自己（82966）；43612 有一条到
`lb-140-82-116-4-sea.github.com:https` 的 **ESTABLISHED 但已停滞**的连接。
→ 超时杀掉的是最外层 git，**孙进程 `git-remote-http` 存活并继续持有 `.git/shallow.lock`**
→ 之后每次 fetch 秒失败 → **永远无法自愈**。

第二个 bug：`except subprocess.CalledProcessError` **抓不到 `TimeoutExpired`**
（两者无继承关系），所以超时根本不会走 re-clone 兜底，直接失败。
（同文件 L578 的 `ls-remote` 路径其实已经正确处理了 `TimeoutExpired`。）

**修法（已落地 `git_source_service.py`，+58/-6）**：

1. `_GIT_HTTP_GUARDS`：`-c http.lowSpeedLimit=1000 -c http.lowSpeedTime=30`
   —— **让 git 自己中止停滞传输**，治本（不再产生需要超时去杀的进程）。
2. `_GIT_ENV`：`GIT_TERMINAL_PROMPT=0` —— daemon 无 TTY，禁止卡在凭证交互
   （与同文件既有实践一致）。
3. `_clear_stale_locks(repo_dir)`：fetch 前清 `.git/*.lock` 和 `.git/objects/*.lock`，
   **只清 mtime 超过 `STALE_LOCK_AGE_SEC=300` 的**，避免误删活锁。
4. `except (CalledProcessError, TimeoutExpired)` —— 补上超时兜底。

实测 `_clear_stale_locks`：陈旧锁被删、新鲜 `index.lock` 保留、无 `.git` 返回 `[]` 不崩。

**注意：`protocol.version=0` 不是原因**（我一开始怀疑它，实测否掉了）：
`ls-remote` 带 pin 1.373s / 不带 1.644s，两者无差异。git 2.55.0。

**踩坑**：`find -maxdepth 3` 扫不到锁——锁在 `src_x/repo/.git/xxx.lock`，从 sources 起算
深度是 4，**扫空了会误判成「无锁」**。另外我的诊断 fetch 用了 `timeout 25`，
被 timeout 杀掉的 git 同样会留下锁，**我的排查本身可能新增了锁**，清理时要一并处理。

**线上状态**：清锁后 sync 已跑通（0 进程、0 锁、无新报错，22:34:18 正常发布）。
但 gateway 仍是 22:12 启动的**旧代码**，代码修复要再重启一次才生效。
